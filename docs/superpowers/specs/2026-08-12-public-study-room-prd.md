# 公网自习室 PRD

> 状态：待评审　|　替代：`2026-08-12-lan-study-room-design.md` 中的「非目标：跨网段 / 公网联机」
> 基础设施：`study.lemon21.cn` 已就绪（DNS + Let's Encrypt + nginx wss 反代，2026-08-12 验证通过）

## 1. 背景与目标

现有自习室是纯局域网方案（UDP 发现 + TCP 直连），只覆盖「同一个 WiFi」的场景。
实际使用中，同学分散在不同宿舍楼、不同城市、在家和在校，同一局域网这个前提经常不成立。

本次改造把自习室接入自有服务器，让**任意网络下的用户都能一起自习**，并引入公共大厅解决「想自习但没有伴」的冷启动问题。

### 成功标准

- 用户不需要知道对方 IP、不需要在同一网络，打开大厅就能加入正在自习的房间。
- 从点击「随机加入」到看见别人的猫在写字，**不超过 3 秒**。
- 全程不需要注册、登录、填任何个人信息。

### 非目标

- 账号体系、好友关系、跨会话历史排行榜（本期明确不做）
- 文字 / 语音 / 图片 / 文件传输（**永久不做**，这是反广告的根本保证）
- 服务端持久化用户数据（首版全内存，重启即清空）

## 2. 已确认决策

| 决策项 | 结论 | 依据 |
| --- | --- | --- |
| 域名 | `study.lemon21.cn` | `.cn` 已备案、DNSPod 解析干净；`.xyz` 在大陆 DNS 被污染，不可用 |
| 账号 | 不要 | 进房顺序即身份，不做跨会话累积就不需要账号 |
| 房内排序 | 按进房顺序 | 取代原设计的「专注时长排行榜」 |
| 大厅排序 | 按当前人数降序 | 按创建时间排会让刷房者永占顶部 |
| 房主离开 | 自动顺延给下一位 | 服务端持有权威状态，顺延成本极低 |
| 随机加入 | 提供 | 解决「想自习但大厅里不知道进哪个」 |
| 局域网模式 | 保留 | 服务器不可用时的降级兜底 |
| 数据持久化 | 首版不做 | 不碰 MySQL，不产生隐私合规义务 |

## 3. 架构变更：权威从房主转移到服务器

这是本次改造的核心，其余功能都是它的推论。

### 变更前（局域网）

```
房主进程 = TCP server = 唯一权威状态
访客进程 = TCP client = 状态镜像
```

房主退出 → 广播 `bye` → 所有连接断开 → 房间消失。

### 变更后（公网）

```
服务器 = 唯一权威状态（内存）
所有客户端 = WebSocket client = 状态镜像
「房主」退化为一个角色标记（hostId 字段）
```

推论：

1. **房主顺延几乎是免费的**——服务器只需把 `hostId` 指向名册里的下一位，无需重连、无需选举。
2. 房主掉线不影响其他人的连接，房间继续存在。
3. 服务端可以强制执行所有规则（限流、清洗、计时），客户端无法伪造。

### 客户端改造点

`src/main/studyRoom/service.ts` 增加一种连接模式，与现有的 hosting / joined 并列：

- `hosting` / `joined`：局域网模式，保留现有全部逻辑
- `online`：公网模式，通过 wss 连接服务器，本地只做状态镜像

`protocol.ts` 的文本清洗、加油白名单、房间码编解码是纯函数，**服务端直接复用同一份代码**，保证两端规则一致。

## 4. 功能规格

### 4.1 公共大厅

进入自习室页面时展示当前活跃房间列表。

| 字段 | 说明 |
| --- | --- |
| 房间名 | 经 `sanitizeRoomName` 清洗后的文本，≤16 字 |
| 当前人数 / 上限 | 上限沿用 `STUDY_ROOM_MAX_MEMBERS`（24） |
| 正在专注人数 | 房内 phase 为 work 且 running 的人数 |
| 房间累计专注 | 分钟数，用于人数相同时的次级排序 |

规则：

- **排序**：当前人数降序 → 房间累计专注时长降序 → 创建时间升序。
- **空房间不展示**：成员数为 0 立即从大厅移除并销毁。
- **不展示昵称**：大厅只暴露房间名一处自由文本，减少广告面。
- 列表通过已建立的 wss 连接推送，进房前后都保持更新。

### 4.2 房主顺延

触发条件：房主断开连接（主动离开、网络中断、进程退出）。

处理：

1. 服务端把 `hostId` 指向**名册中进房顺序最靠前的剩余成员**。
2. 房间名、集体目标、房间累计专注时长、成员的房内专注时长**全部保留**。
3. 向房内广播一条 notice：「XX 离开了，YY 成为新房主」。
4. 若离开的是最后一人 → 销毁房间，从大厅移除。

房主特权仅限：设置集体目标。不设踢人功能（无账号体系下踢人容易被滥用，且加入本身无门槛，踢了也能立刻回来）。

### 4.3 随机加入

一次点击直接进入一个合适的房间，不需要用户在列表里挑。

匹配优先级：

1. **人数 2-6 且未满**的房间中随机选一个 —— 有氛围又不嘈杂，体验最好
2. 人数 1 的房间 —— 帮落单的人凑成伴
3. 人数 7 及以上且未满的房间
4. **一个可用房间都没有 → 自动创建一个公开房间**，用户成为第一位成员

第 4 条是关键：冷启动阶段大厅必然是空的，此时返回「暂无房间」等于把用户劝退。自动开房让他成为大厅里的第一个人，后来者就能匹配到他。

自动创建的房间名使用系统预设（如「一起自习」+ 序号），**不允许用户在此路径下自定义**，避免随机加入被当成建房入口滥用。

### 4.4 反滥用（无账号前提下）

公共大厅让房间名从「同一 WiFi 可见」变成「全网可见」，它是本产品唯一的公开广告位。

| 手段 | 规则 | 实现位置 |
| --- | --- | --- |
| 文本清洗 | 房间名、昵称复用 `normalizeDisplayText` + `looksLikePromotion` | 服务端强制执行，客户端仅做即时提示 |
| 空房即焚 | 成员数为 0 立即销毁 | 广告房必须有人挂着才可见，成本陡增 |
| IP 并发限制 | 同一 IP 同时只能持有 1 个房间 | 服务端按 `X-Forwarded-For` 判定 |
| 创建频率限制 | 同一 IP 每 10 分钟最多创建 3 个房间 | 服务端滑动窗口 |
| 排序抑制 | 大厅按人数降序，无人房间自然沉底 | 见 4.1 |
| 加油节流 | 沿用 `STUDY_ROOM_CHEER_COOLDOWN_MS`（3 秒） | 服务端强制 |
| 帧大小限制 | 沿用 `STUDY_ROOM_MAX_FRAME_BYTES`（16KB） | 服务端强制 |
| 计时防伪 | 沿用 `STUDY_ROOM_MAX_FOCUS_STEP_SEC`（15 秒） | 服务端按真实时间戳累计，不信客户端上报 |

nginx 层已具备 IP 透传条件（`/ws` 配置了 `X-Real-IP` 与 `X-Forwarded-For`）。

## 5. 协议

传输：**wss**（`wss://study.lemon21.cn/ws`）。禁止裸 TCP 或 ws——公网明文会让昵称、专注状态、房间信息全部可被中间人读取和篡改。

编码：沿用 NDJSON，与局域网模式一致，`protocol.ts` 的编解码函数直接复用。

### 客户端 → 服务端

| type | 载荷 | 说明 |
| --- | --- | --- |
| `hello` | 昵称、猫 ID、协议版本 | 连接后首帧 |
| `lobby` | — | 订阅大厅列表 |
| `create` | 房间名、目标分钟 | 创建房间 |
| `join` | 房间 ID | 加入指定房间 |
| `quickJoin` | — | 随机加入，见 4.3 |
| `leave` | — | 离开房间（保持连接） |
| `focus` | phase、running、剩余秒数 | 专注状态上报，同阶段 3 秒节流 |
| `goal` | 目标分钟 | 仅房主可用 |
| `cheer` | cheerId、目标成员 ID（可空） | 白名单枚举，非白名单直接丢弃 |

### 服务端 → 客户端

| type | 载荷 | 说明 |
| --- | --- | --- |
| `welcome` | 分配的成员 ID、服务端协议版本 | |
| `lobby` | 房间列表（已排序） | 增量推送 |
| `roster` | 房间信息 + 成员数组（按进房顺序） | |
| `cheered` | 发送者、接收者、cheerId | |
| `notice` | 事件类型 + 展示文本 | 进出房、房主顺延、目标达成 |
| `error` | 错误码 + 可展示文案 | 房间已满、房间不存在、被限流等 |

**协议版本不匹配时服务端必须明确拒绝并给出可读提示**，不能让旧客户端静默连上后行为异常。

## 6. 前置修复项（上线前必须完成）

以下是本次改造直接依赖的既有缺陷，不修会在公网场景放大：

1. **反广告规则误杀**（`protocol.ts:88-112`）
   - `.com` / `.cn` / `.net` / `.top` 等域名后缀经 `compactForMatch` 压紧后退化为纯字母匹配，`laptop`、`Janet`、`workshop` 等正常昵称被判为广告。
   - 数字占比规则会误杀 `2026考研`（压紧后长度 6、数字 4 个，4×2 > 6），而这恰是自习场景最典型的昵称。
   - 局域网熟人场景误杀可以忍，公共大厅是陌生人场景，触发频率会高得多。
2. **`studymedia` 协议缺路径校验**（`index.ts:615-624`）
   - 服务端开始下发陌生人可控内容后，这个缺口的风险等级上升，需限定可访问目录。
3. **明文传输**：客户端必须走 wss，不得回落到裸 TCP。

## 7. 验收标准

### 功能

- [ ] 两台不同网络（如手机热点 + 家庭宽带）的设备能进入同一房间并互相看到状态
- [ ] 大厅列表按人数降序，人数相同时按累计专注时长排序
- [ ] 房主关闭应用后，房间存续，房主标记顺延给进房顺序次位，房间名与目标不变
- [ ] 最后一名成员离开后，房间从大厅消失
- [ ] 大厅为空时点击随机加入，自动创建房间并进入
- [ ] 大厅有 2-6 人房间时，随机加入优先进入该类房间
- [ ] 昵称 `2026考研`、`laptop` 可正常使用（前置修复项验收）
- [ ] 房间名含链接或联系方式时被服务端拒绝，且返回可读理由

### 异常与边界

- [ ] 服务器不可达时，客户端明确提示并可降级到局域网模式
- [ ] 断网重连后能回到原房间，房内专注时长不清零
- [ ] 房间满员（24 人）时加入返回明确错误而非静默失败
- [ ] 同一 IP 创建第 2 个房间时被拒绝并说明原因
- [ ] 旧版本客户端连接时收到协议版本不匹配提示

### 非功能

- [ ] wss 证书校验通过，无证书告警
- [ ] 随机加入端到端耗时 < 3 秒
- [ ] 服务端单房间 24 人时，状态广播不出现 O(N²) 放大（需实现广播合并）

## 9. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 服务器故障 | 公网自习室完全不可用 | 保留局域网模式作降级；客户端明确区分「服务器故障」与「没有房间」 |
| 域名硬编码 | 换域名后旧版本全部失效 | 服务端地址做成可配置项 + 内置兜底列表 |
| 广告绕过清洗 | 大厅出现推广房间 | 空房即焚 + 人数排序已大幅削弱收益；必要时加人工下架开关 |
| 单机资源 | 服务器 4 核 3.6G，磁盘已用 59% | 全内存无落库；先实现广播合并再开放 |
| 未成年人内容合规 | 公开服务的监管要求 | 无自由文本互动（仅房间名/昵称经清洗），风险面已最小化；如后续加任何文本功能需重新评估 |
